# Ollama AI 模式 + 重生成随机化 — 规格 (SPEC)

> 版本：v1.2 · 日期：2026-08-30
> 状态：`ready-for-agent`
> 关联：`docs/adr/0002-ollama-ai-mode.md`、`CONTEXT.md`、`.scratch/ollama-ai-mode/issues/01~04`

## Problem Statement

结果页的「重生成」和「清空锁餐重生成」按钮看起来没有反应：点击后计划毫无变化。原因是生成器是纯确定性函数——同样的身体数据、同样的锁餐必然产出完全相同的计划，不存在任何随机性。用户希望结果能"换一批"，同时希望计划生成能接入本机 Ollama 上的 qwen3 模型，让 AI 参与菜谱设计，而不是只有死板的固定搭配。

## Solution

引入**双模式生成**：

1. **算法模式（默认）**：保留现有本地营养计算引擎，但给生成器加一个可注入的**生成 seed**——首次生成用固定 seed（与现状一致、演示可复现），每次「重生成」换新 seed，让未锁餐次在同类食材池内轮换（鸡胸 → 牛肉 → 鱼…）且分量小幅浮动（±10% 后收敛达标）。锁餐语义不变。
2. **AI 模式（表单「AI 生成」开关）**：接入本机 Ollama 的 qwen3:8b。LLM 只做**受控选材**——从本地食材库候选清单里挑选每餐食材 id（不能发明库外食材）；分量仍由算法引擎按宏量目标分配。因此营养数字 100% 由算法保证，LLM 幻觉被隔离在"选什么食材"这一层。已锁定餐次会告知 LLM 以便避让，生成后仍以锁定内容覆盖。
3. **降级与透明**：Ollama 未运行、模型缺失或 90 秒超时时，自动回退算法引擎，结果页明示「本次由本地引擎生成」，不报错。

## User Stories

1. 作为用户，我希望首次生成计划时结果稳定可复现，以便在求职演示中每次演示同一套输入得到同一份计划。
2. 作为用户，我希望在未锁任何餐时点「重生成」，未锁餐次的食材会换一批，以便看到计划确实在变化。
3. 作为用户，我希望点「清空锁餐重生成」时所有锁餐先被清空、再完整重新生成，以便一次性换个全新计划。
4. 作为用户，我希望锁了某几餐后点「重生成」，被锁餐次内容保持不变、其余餐次重新搭配，以便在保留喜欢餐次的同时换新。
5. 作为用户，我希望锁餐后多次重生成，锁定餐次始终纹丝不动，以便锁定是可靠的。
6. 作为用户，我希望表单里有一个「AI 生成」开关，开启后生成走本地 Ollama，以便让 AI 参与菜谱设计。
7. 作为用户，我希望 AI 模式生成的计划里每餐食材都是我认识的常见食材，以便不会出现生僻或编造的食材。
8. 作为用户，我希望 AI 模式下每餐的克数与宏量依然准确达标（热量/蛋白偏差在既有容差内），以便 AI 不破坏营养计算的可信度。
9. 作为用户，我希望 AI 模式下锁餐也会被尊重：提示词告知 LLM 已锁餐次，生成后仍以锁定内容覆盖，以便锁餐在任何模式都生效。
10. 作为用户，我希望开启 AI 生成但 Ollama 未运行时，应用不报错而是自动回退到算法计划，并明确告诉我本次是本地引擎生成的，以便我知道发生了什么。
11. 作为用户，我希望 AI 生成期间有清晰的等待提示（"本地模型生成中，约需 1 分钟…"），以便我知道它在工作而不是卡死。
12. 作为用户，我希望 AI 返回了库外食材或无效结构时不产生坏结果，而是回退到算法计划，以便结果永远是完整的。
13. 作为开发者，我希望默认 seed 下旧单测全部通过，以便算法随机化不破坏既有回归保障。
14. 作为开发者，我希望生成器、提示词构造、AI 输出校验都是可单测的纯函数，以便用项目现有的 node:test 风格覆盖。
15. 作为开发者，我希望 AI 模式的接入点是现成的 provider 注册表，以便以后加新模型（云端或本地）只增一行配置。

## Implementation Decisions

- **双模式路由**：生成接口接受 `useAI` 入参（布尔）。`useAI=false`（默认）直接走算法引擎；`useAI=true` 先探测 LLM provider，失败/超时回退算法引擎。响应携带 `usedAI` 与降级标记，供前端提示。
- **生成器 seed 机制**：`generateWeek` 增加可注入 seed 参数。缺省/固定 seed 时输出与现状逐字节一致；seed 变化时：(a) 每餐食材在同类池内按 seed 派生偏移轮换；(b) 分量小幅浮动——在迭代锚点（碳脂热量份额）上施加 ±10% 扰动后收敛（初值抖动会被定点迭代抹平，故锚定份额，同食材下分量也有真实差异），宏量照旧达标。锁餐分支先于随机化执行，锁定餐不受影响。
- **受控选材协议**：AI 输出 Schema 改为仅食材 id 清单（决策-rich，来自访谈原型）：
  ```json
  { "days": [ { "meals": [ { "items": [ { "id": "chicken_breast" } ] } ] } ] }
  ```
  不含克数、不含宏量。服务端校验全部 id 存在于食材库，任一非法 → 整体抛错回退本地；合法 → 由算法引擎按宏量目标分配分量并组装完整 plan。
- **提示词构造**：LLM 输入 = 用户数据 + 计算依据（calc 摘要）+ 食材库候选清单（id + 名称，按池分组）+ 已锁定餐次摘要（如"第1天 早餐 已锁定：鸡胸肉 150g + 米饭 200g"），并要求避让重复。qwen3 请求体显式 `enable_thinking: false`，避免思考过程混入破坏 JSON 解析。
- **provider 注册**：在既有 provider 注册表增加 ollama（baseURL 指向本机 Ollama OpenAI 兼容端点，model `qwen3:8b`）。探测顺序：云端真实 key（DeepSeek / 通义）→ Ollama。Ollama 连接被拒应快速失败，复用现有回退路径。
- **超时与等待**：AI 调用超时 15s → 90s；前端在 AI 模式下展示进度文案。
- **降级提示**：曾请求 AI 但最终走了算法引擎时，结果页显示提示条「本次由本地引擎生成」。

## Testing Decisions

- **好测试的标准**：只断言外部行为——输出宏量偏差在既有容差内、结构完整、seed 确定性/差异性、锁餐不变性、AI 输出校验通过/拒绝；不测内部实现细节（不断言具体用了哪个池、哪轮迭代）。
- **接缝（3 个 lib 纯函数，均已与用户确认）**：
  1. `generateWeek(input, locked, seed)`——算法随机化 + 锁餐 + 分量收敛。
  2. `buildMessages` / `detectProvider`——提示词内容（食材清单、锁餐摘要）与 provider 探测顺序。
  3. `resolveAIIds(plan, foods)`（新增纯函数）——AI 输出的 id 校验与映射，含非法 id 拒绝。
- **测试模块**：`generator.test.js`（增补 seed 用例）、`prompt.test.js`（新建）、AI 校验随其宿主模块建测试文件。
- **先例**：`generator.test.js` / `nutrition.test.js` 现有风格（`node:test` + `assert/strict`，断言热量偏差 ≤2.6%、蛋白偏差 ≤1%、结构完整性）。API 路由与 UI 不建测试（项目现状即无此类先例），保持薄胶水。

## Out of Scope

- 流式输出（SSE）——等待体验用进度文案解决，不做逐餐流式渲染。
- 多模型选择 UI、云端 LLM 切换面板。
- Ollama 安装 / 模型拉取 / 服务自启——仅文档说明（需 `ollama pull qwen3:8b` 且服务运行）。
- 营养公式与宏量目标口径的任何改动。
- 锁餐食材强制去重（仅靠 prompt 提示 LLM 避让，不做硬性规则）。
- API 集成测试与前端组件测试（沿用项目无先例现状）。
- 移动端响应式、分享图、进度追踪等既有范围外项。

## Further Notes

- Ollama 官方库**没有 qwen-3.5**（访谈中核实）；最新主线为 qwen3 系列，选定 `qwen3:8b`（约 5-6GB 显存）。
- 本机已装 Ollama（client 0.30.4）但服务默认未启动；演示前需先启动服务并确保模型已拉取。
- 首次生成固定 seed 是本轮"可复现演示 + 单测稳定"的关键：默认路径与 v1.0 行为逐字节一致。
- 随机化必须可注入而非全局 `Math.random()`，否则破坏 37 个既有用例的确定性。
